# Второй этап: реализованная обучаемая подсистема

## Что работает

- Согласие на обучение включается отдельно от истории рекомендаций на `/game/{id}/strategies`; по умолчанию выключено. При отзыве согласия сохранённые для этого производителя эпизоды удаляются. Ранее обученный агрегированный артефакт не может быть автоматически «разобучен»; перед повторным обучением можно удалить том `strategy_models` вручную.
- При подтверждении параметров производства (а не при запросе совета) фиксируются доступный игроку `StrategySnapshot`, фактически выбранное действие и день решения. Старые партии без таких записей не используются для ретроспективного обучения. Игроки других игр и скрытые параметры покупателя в признаки не входят.
- `ml/learning.py` берёт только разрешённые эпизоды **завершённых** игр; метка — сумма *фактических продаж* за следующий завершённый цикл. Циклы с пропущенными дневными результатами отбрасываются. Минимум для попытки обучения: 12 игр и 60 полных циклов. Тренировочная, валидационная и тестовая выборки разделены по целым играм. Сравниваются последние продажи, Ridge, Random Forest, CatBoost и LightGBM; лучший кандидат активируется, только если его MAE на валидации меньше базового прогноза и действующей модели на **той же** валидации. Тестовый MAE только публикуется в отчёте. Интервал строится по 90-му процентилю абсолютной ошибки на валидации — это не гарантия 90% покрытия для новых игр.
- Результаты сравнения находятся в `strategy_models:/app/artifacts/last-report.json`, действующая версия — в `champion.joblib`. Фоновая проверка новых завершённых игр работает раз в час, следующая версия обучается после трёх новых завершённых игр; пороги являются стартовыми и подлежат проверке по реальным данным.
- Для одного запроса Java оценивает до трёх **уже проверенных правилами** альтернатив с одним и тем же снимком. Действующая модель меняет оценки продаж за цикл и условных денег и, если применима ко всем карточкам, порядок по нижней оценке денег. Другие модели, обошедшие базовый прогноз на валидации, могут предложить свой выбор из тех же безопасных альтернатив; расхождения показываются игроку без голосования. При отсутствии модели, недоступности сервиса, выходе параметров за изученные диапазоны или некорректном ответе остаются правила. Финансовые ограничения и выбор курса без автоматического производства сохранены.
- При указании `STRATEGY_LLM_URL`, `STRATEGY_LLM_MODEL`, `STRATEGY_LLM_KEY` подключается совместимый с OpenAI Chat Completions сервис для короткого текстового пояснения проверенных карточек. Числа из ответа отвергаются; при ошибке остаются объяснения карточек. LLM не принимает экономических решений.

## Запуск и проверка

`docker compose up --build -d --wait` запускает Java, PostgreSQL и локальный ML-сервис; существующий том базы не удаляется. До накопления достаточного количества разрешённых завершённых партий ML-сервис отвечает `503` на `/predict`, а советы работают по правилам. Для одноразовой попытки обучения: `docker compose exec ml python -m learning`. Для просмотра результатов: `docker compose exec ml python -c 'from pathlib import Path; print(Path("/app/artifacts/last-report.json").read_text())'`. ML-сервис доступен только внутри сети Compose. Перед использованием реальных данных для обучения следует выделить ему отдельную БД или пользователя PostgreSQL с правами только на чтение нужных таблиц (в демонстрационном Compose используется общий пользователь).

Java-тесты запускать на **отдельной PostgreSQL** (например, `./mvnw -Dspring.datasource.url=jdbc:postgresql://localhost:5436/diploma test`), потому что интеграционные тесты создают схему. Python-тесты: `docker run --rm -w /tests --mount type=bind,src="$PWD/ml",dst=/tests,readonly -e PYTHONPATH=/tests:/app -e STRATEGY_AUTO_TRAIN=false e-game-ml python -m unittest -v test_learning`.

## Ограничения проверки

Сейчас в репозитории нет разрешённого корпуса завершённых игр, поэтому **реальная модель ещё не обучена** и утверждать превосходство над правилами нельзя. Тестирование на синтетических примерах проверяет обучение, разделение по играм и отказ при нехватке данных, но не пользу советов на игроках. Эксперименты со специализированной моделью непроданного остатка, парные игровые прогоны с одинаковым seed и проверка покрытия интервалов на новых партиях остаются следующими экспериментами из `STRATEGY_AGENTS_STAGE2_TASK.md`. RAG не внедрён.
