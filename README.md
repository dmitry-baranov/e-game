# Economic Concurrent Game (e-game)

Веб-игра — симуляция конкуренции производителей за покупки одного виртуального покупателя. Администратор задаёт параметры рынка и участников, а игроки управляют производством, ценой, качеством, ассортиментом и рекламой. По мере прохождения игровых суток приложение моделирует выпуск и продажу товаров, начисляет выручку, учитывает кредиты и налог, а в конце сравнивает финансовые результаты предприятий.

Интерфейс и формы — на русском языке. Проект построен на Spring Boot 2.5.6, Spring MVC, Spring Security, Spring Data JPA, FreeMarker и PostgreSQL 14. Графики на страницах строятся с помощью Chart.js; стили используют Bootstrap из CDN.

## Быстрый запуск через Docker

Нужны Docker и Docker Compose (`docker compose`). Свободными должны быть порты **8080** (приложение) и **5435** (PostgreSQL). Java и Maven на компьютере не требуются.

```bash
docker compose up --build -d
docker compose ps
```

После запуска:

- регистрация: <http://localhost:8080/sign-up>;
- вход: <http://localhost:8080/sign-in>;
- профиль после авторизации: <http://localhost:8080/profile>.

Compose поднимает `db` и `app`, дожидается готовности базы перед запуском приложения. Внутри сети Compose приложение подключается к `db:5432/diploma`; с компьютера база доступна на `localhost:5435`. Имя базы, пользователь и пароль для локального запуска заданы в `compose.yml` (`diploma`, `postgres`, `postgres`).

Полезные команды:

```bash
docker compose logs -f app  # логи приложения
docker compose down         # остановить и удалить контейнеры, сохранив данные
docker compose down -v      # удалить контейнеры И volume с данными PostgreSQL
```

При запуске из каталога `e-game` именованный volume обычно называется `e-game_postgres_data`. Если вы уже запускали проект из каталога с другим именем, Compose рассматривает его как другой проект и создаст новый volume. Чтобы использовать прежнее имя Compose-проекта, можно указать `docker compose -p <старое-имя-проекта> ...`; данные между разными volume автоматически не переносятся.

## Автономные игры ботов (экспериментальный режим)

Эксперименты используют **отдельные** PostgreSQL, экземпляр приложения и том моделей из `compose.experiment.yml`. Они не запускаются из обычного `compose.yml` и не читают человеческие партии:

```bash
docker compose -p e-game-lab -f compose.experiment.yml up --build -d
```

Откройте <http://localhost:8081/sign-up> и зарегистрируйте первого администратора **в новой экспериментальной базе**, затем войдите и перейдите на <http://localhost:8081/admin/bot-experiments>. Задайте число качественно завершённых игр, параллелизм (до 10), число ботов (до 30), границы игровых дней, seed, рынки и состав политик (названия и примеры указаны в форме), лимит попыток (`0` = автоматически). Посмотрите предпросмотр сценариев и запустите серию. Статус, последние игры, ошибки, финансовый отчёт и пауза/продолжение/остановка доступны на странице серии. После рестарта приложения незаконченная игра возобновляется с сохранённого дня; день выполняется в одной транзакции. Используйте **один** экземпляр экспериментального приложения для этой очереди.

Горизонт каждой игры выбирается до старта по сценарию. В целевой счётчик попадают игры, дошедшие до горизонта, с минимум двумя производственными циклами на бота. Остальные помечаются `INCOMPLETE` или `ERROR` и не попадают в обучение. После первых нескольких десятков игр оцените длительность и распределение продаж перед масштабированием до 1000: параметры генератора пока пилотные. На странице видны итоги после долгов и результат на игровой день.

Экспериментальный ML-сервис запускается с отключённым автообучением. После как минимум 12 завершённых игр сбора данных нажмите **«Обучить»** на странице серии: обучение выполняется в фоне, отчёт обновляется там же. Это минимальный технический порог; для обучения также нужно 60 полных циклов. Артефакт сохраняется **только** в экспериментальном томе. Режим `EVALUATE` создаёт пары с одинаковым seed: первый бот следует правилам либо модели, остальные политики фиксированы; требуется чётное число игр и обученная модель. Парные игры никогда не включаются в обучающую выборку. При неприменимости прогноза бот использует правила, а страница показывает число таких возвратов; если модель так и не использовалась, пара не засчитывается. Версия модели записывается для серии и проверяется при выборе действия; не запускайте переобучение во время её оценки. Перенос модели в обычное приложение выполняется только после отдельной проверки качества и не происходит автоматически.

```bash
docker compose -p e-game-lab -f compose.experiment.yml logs -f experiment-app
docker compose -p e-game-lab -f compose.experiment.yml down  # тома с данными сохраняются
```

## Первый вход и роли

1. Зарегистрируйте **первый** аккаунт на `/sign-up`: в пустой базе он автоматически получает роль `ADMIN`. SQL-запрос не требуется.
2. Зарегистрируйте отдельные аккаунты игроков: все последующие регистрации получают роль `USER` — производитель. Администратор выбирает игроков при создании игры. Войти можно по email и паролю на `/sign-in`; профиль доступен на `/profile`.

## Как проходит игра

### 1. Настройка рынка

Администратор в профиле открывает **«Новая игра»** (`GET /game`) и выбирает зарегистрированных участников. В форме указываются:

| Группа | Параметры |
| --- | --- |
| Время и финансирование | длительность игровых суток в минутах, ставки инвестиционного и оборотного кредитов, срок инвестиционного кредита, налог с продаж |
| Производство и реклама | базовая себестоимость, цена рекламы и стоимость создания производственной мощности |
| Покупатель | максимальное количество ещё не изношенных товаров, дневной бюджет, срок службы товара максимального качества |
| Выбор товара | веса ассортимента, качества, рекламы и привычки к производителю; число дней для учёта привычки |

Форма ожидает сумму четырёх весов, равную 1. Одновременно создать новую игру нельзя, пока существует игра в состоянии, отличном от `FINISHED`. После создания игра получает статус `CREATED`, а для выбранных игроков создаются предприятия.

### 2. Решения производителей

Игрок на странице своей игры (`/game/{id}`) сначала открывает предприятие: выбирает объём партии, ассортимент, качество, цену, мощность производства и рекламу. До ввода параметров можно посмотреть три понятных **стартовых сценария** на `/game/{id}/strategies`. Форма рассчитывает ориентировочные себестоимость, затраты на рекламу, длительность производственного цикла и размер стартового **инвестиционного кредита**. Сервер независимо пересчитывает стоимость, срок цикла и размер кредита перед созданием производства.

После открытия предприятия игрок может задавать новые производственные циклы через `/game/{id}/production-parameters`: менять параметры партии, цену и рекламу, финансировать затраты из баланса и при необходимости брать **оборотный кредит**. Формы помогают рассчитать затраты и минимальную сумму кредита; интенсивность и длительность рекламы должны быть одновременно нулевыми либо обе ненулевыми. Сервер не позволяет открыть новый цикл до окончания текущего.

На странице игры доступны баланс и долги, собственные продажи/выпуск/остатки по дням и ближайшие платежи, история параметров производства, графики выручки и рекламной активности, а также сведения о конкурентах и их выручке. Данные графиков обновляются HTTP-запросами из браузера.

### Советы и собственные планы

На странице `/game/{id}/strategies` игрок **по запросу** получает до трёх альтернатив: расходы, условный риск, причины и ограничения данных. Финансовый, рыночный и производственный агенты работают с отдельным снимком разрешённых игроку данных; они не вызывают торговые сессии. При наличии минимум трёх завершённых дней показываются ориентиры наблюдаемых продаж, при семи — 20-й/50-й/80-й процентили; до трёх дней числовой прогноз не строится. Изменение цены или реклама не считаются гарантией роста спроса.

Кнопка **«Выбрать стратегию»** сохраняет только название курса и не отправляет игровую форму. В конструкторе можно сравнить и сохранить свой план; сохраняемый план не зависит от настройки истории советов. Переключатель истории рекомендаций по умолчанию выключен: советы без него доступны, но записи появляются только после включения и остаются видимыми после выключения.

### 3. Торговые сессии и расчёты

Администратор на странице игры запускает/останавливает торговые сессии. Один цикл планировщика соответствует одним игровым суткам; интервал задаётся в минутах при создании игры (`timeUnit`). Статусы игры: `CREATED` → `STARTED` ↔ `STOPPED` → `FINISHED`.

В течение суток приложение:

1. Увеличивает номер игрового дня, производит партии товаров по действующим параметрам и учитывает остатки на рынке.
2. Ранжирует предложения по качеству, рекламе, ассортименту, привычке покупателя и цене. Модель единого покупателя ограничивает покупки дневным бюджетом, доступными товарами и пределом насыщения; купленные товары со временем изнашиваются в зависимости от качества.
3. Зачисляет выручку производителям, сохраняет продажи и статистику. По графику списывает платежи по кредитам; налог с продаж рассчитывается каждые 30 игровых суток.

Администратор может завершить игру с панели управления: активный таймер останавливается. На странице итогов участники сортируются по финансовому результату: **баланс минус оставшиеся долги по инвестиционному и оборотному кредитам**.

Игровой день, товарные остатки, продажи, баланс и платежи сохраняются в PostgreSQL в одной транзакции торгового дня. После перезапуска текущий день и остатки восстанавливаются, **таймер остаётся на паузе** до явного запуска администратором. Существующие игры предыдущей версии не мигрируются: при фактическом развёртывании новой версии нужна новая пустая БД и повторная регистрация аккаунтов. Текущая БД автоматически не очищается.

## Основные страницы и маршруты

| Метод и путь | Назначение |
| --- | --- |
| `GET /sign-up`, `POST /sign-up` | регистрация |
| `GET /sign-in`, `POST /sign-in` | форма входа и обработка входа Spring Security |
| `GET /profile`, `GET /profile/edit`, `POST /profile` | профиль и изменение имени |
| `GET /game`, `POST /game` | создание игры администратором |
| `GET /game/{id}` | страница игры для участника или администратора |
| `GET /game/{id}/strategies`, `POST .../recommend`, `POST .../compare` | личные сценарии и запрос советов |
| `POST .../save`, `POST .../delete/{planId}`, `POST .../select`, `POST .../history-preference`, `GET .../history/{historyId}` | личные планы, курс и необязательная история |
| `POST /game/{id}/initial-production-parameters` | открытие предприятия участником |
| `GET/POST /game/{id}/production-parameters` | новые параметры производства |
| `GET /game/{id}/trading-sessions/start/{timeUnit}`, `GET /game/{id}/trading-sessions/stop` | управление игровыми сутками из панели администратора |
| `POST /game/{id}/finish` | завершение игры администратором |
| `GET /games`, `GET /{accountId}/games` | списки игр в JSON для страниц профиля |
| `GET /game/{id}/manufacturers-parameters`, `GET /manufacturer/{id}/competitors-data` | параметры производителей и конкурентов в JSON |
| `GET /game/{id}/financial-status/{accountId}`, `GET /game/revenue-data/{manufacturerId}`, `GET /game/{gameId}/advertising-intensity/{accountId}` | финансовые данные и ряды для графиков в JSON |

Это маршруты веб-приложения, а не отдельный документированный публичный API. Доступ к части действий ограничен ролями через `@PreAuthorize`; подробности — в соответствующих контроллерах.

## Локальный запуск без Docker-приложения

Требуются **Java 17** и PostgreSQL (например, только сервис базы из Compose). Установленный Maven не нужен: `./mvnw` скачивает Maven 3.8.8 при первом запуске.

```bash
docker compose up -d db
./mvnw clean package
java -jar target/diploma-0.1.jar
```

При запуске JAR вне Docker настройки `src/main/resources/application.properties` по умолчанию используют `localhost:5435/diploma`, пользователя/пароль `postgres`/`postgres` и **порт приложения 80**. Чтобы запускать без прав на порт 80, задайте порт явно:

```bash
SERVER_PORT=8080 java -jar target/diploma-0.1.jar
```

Не запускайте локальный JAR на порту 8080 одновременно с сервисом `app` из Compose. Параметры подключения можно переопределять стандартными переменными Spring Boot: `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, `SERVER_PORT`.

## Структура проекта

```text
src/main/java/ru/itis/diploma/
  controller/       страницы и HTTP-маршруты
  dto/              данные форм и ответов
  model/            сущности JPA: аккаунты, игры, производители, товары, платежи, статистика
  repository/       доступ к PostgreSQL через Spring Data JPA
  service/          игровая логика, покупатель, платежи и статистика
  security/         вход, роли и remember-me
  config/           планировщик и конфигурация сообщений
src/main/resources/
  templates/        страницы FreeMarker (.ftlh)
  application.properties  настройки приложения для локального запуска
  schema.sql        таблицы сессий и remember-me
src/test/           проверки агентов, шаблона, границы доступа и сохранения торгового дня
Dockerfile          сборка JAR и образ приложения
compose.yml         приложение + PostgreSQL
```

JPA с `spring.jpa.hibernate.ddl-auto=update` создаёт/обновляет таблицы предметной области; `schema.sql` содержит таблицы для сессий и токенов входа. Названия пакета `ru.itis.diploma`, базы `diploma` и файла `diploma-0.1.jar` — внутренние имена исходного проекта; имя каталога репозитория на их работу не влияет.

## Проверка

```bash
./mvnw test
./mvnw clean package
docker compose config --quiet
```

Интеграционные тесты проверяют торговый день, сохранение выбора и изоляцию скрытых настроек; для них и проверки загрузки контекста требуется PostgreSQL. Перед запуском тестов поднимите базу (`docker compose up -d db`) либо задайте собственную **тестовую** БД через `SPRING_DATASOURCE_URL`. Новые игры создавайте в пустой базе; тесты с транзакциями откатывают свои игровые данные.
