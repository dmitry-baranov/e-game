# Шестой этап: реализация и результаты проверки

Реализация задания из [аналитики шестого этапа](analitics/STRATEGY_AGENTS_STAGE6_TASK.md), 09.10.2026. При измерениях серия № 20 находилась в статусе `PAUSED`; все пробные игры проводились в отдельном PostgreSQL-контейнере на копиях данных, без изменения её seed/параметров.

## Реализовано

- Java 25 (сборка и исполнение в контейнерах), Spring Boot 4.1.1, Maven wrapper 3.10.0, Jakarta Persistence/Validation, Spring Security 7 с сохранением формы входа, Spring Session JDBC (cookie `SESSION`), текущие управляемые BOM версии PostgreSQL JDBC, Hibernate, Jackson 2 и Lombok. Из старых прямых зависимостей удалены неиспользуемые zip4j, commons-io, commons-fileupload; Jackson 2 пока сохранён через модуль совместимости Spring Boot 4, так как игровые снимки, HTTP DTO и отчёты используют его API. Вызов LLM читает строку HTTP-ответа перед разбором Jackson 2: это устраняет несовместимость с новым HTTP-конвертером.
- ML: Python 3.13, обновлены все восемь прямых пакетов `ml/requirements.txt`; собран arm64-образ и проверены тесты, существующий CatBoost-артефакт в **read-only** экспериментальном томе корректно загрузился новой версией ML (`/health`: `ready=true`, старая версия модели сохранена).
- Оптимизированы запросы на последнее производство/рекламу и семь продаж: `ORDER BY ... LIMIT 1/7` вместо чтения всей истории в Java. Для привычки покупателей SQL суммирует покупки по производителю вместо передачи всех строк приложению. Планировщик выбирает первую ожидающую игру ограниченным запросом. При принятии решений в эксперименте видимые показатели конкурентов рассчитываются один раз на игровой день до применения планов, а не заново для каждого бота; отдельный обычный вызов снимка продолжает проверять владельца и доступные ему данные.
- `src/main/resources/performance_indexes.sql`: пять идемпотентных `CREATE INDEX CONCURRENTLY` для рекламы, продаж, платежей и ожидающих игр. Файл запускается через `psql -f` **вне транзакции**, не автоматически Hibernate. Индексы успешно созданы в обеих действующих БД без остановки их PostgreSQL.
- По умолчанию `EXPERIMENT_VIRTUAL_THREADS=true` выбирает виртуальные потоки Java 25 **только для независимых игр** (при необходимости можно задать `false`). Лимит по сериям сохранён; глобальный семафор ограничивает число одновременно обрабатываемых игр десятью, и работает также для обычного пула. Обработка отдельных ботов в рамках одного дня остаётся последовательной в общей транзакции. Диспетчер обходит активные серии по кругу и при выдаче слотов чередует серии; одновременные игры одной серии координируются блокировкой строки серии при выдаче, а игровые дни — блокировкой строки игры.
- Планировщик обычных торговых игр вместо единственного рабочего потока имеет пул из десяти; задачи завершённых игр удаляются. Пул подключений к PostgreSQL увеличен до 16, чтобы несколько игр могли выполняться параллельно и оставались подключения для интерфейса. Восстановление прерванных игр и обработка сбоев эксперимента проходят в настоящих транзакциях.
- `spring.threads.virtual.enabled=true` включает виртуальные потоки Spring Boot по умолчанию для поддерживаемых им фоновых и веб-задач. Периодические торговые задачи используют собственный **ограниченный** пул из десяти потоков, чтобы не сериализовать fixed-delay задания на одном планировщике и не создавать бесконтрольную нагрузку на БД.
- Износ покупок в течение игрового дня обновляется одним ограниченным текущей игрой SQL `UPDATE` вместо загрузки всех неизношенных покупок и отдельных сохранений; критерий износа и исключение записей с нулевыми покупками сохранены. Граница даты, изоляция игр и нулевые продажи проверяются интеграционным тестом.
- Добавлены частичный индекс по неизношенным покупкам и индекс производителей игры через `CREATE INDEX CONCURRENTLY`; применены к обеим рабочим БД без пересоздания томов.
- Локальная Java 25 из SDKMAN подтверждена командой `./mvnw -version` (`Temurin 25.0.3`). Интеграционная проверка на отдельной PostgreSQL запустила **три серии одновременно, по две игры из каждой, по десять ботов и 30 дней**: все шесть игр завершили 30 дней, у каждой ровно 300 записей статистики, без `ERROR` и дублирования номеров попыток. Зафиксировано перекрытие активных игр; p50 одного дня при этом составила 144–160 мс, p95 — 269–299 мс (проверка корректности, не сравнительный benchmark). Отдельный тест проверяет одновременную выдачу трёх задач планировщиком обычных игр. Полный `./mvnw clean package` на локальной Java 25 прошёл, включая 31 тест.
- В лог приложения после каждого участка обработки игры записываются число завершённых транзакционных дней, p50/p95 длительности дня и общая длительность участка; после паузы и возобновления для одной игры будут отдельные участки. Эти метрики позволят выполнить повторный A/B замер без изменения игровых данных.

## Проверено на изолированной копии

1. `./mvnw clean package` внутри контейнера Java 25: все 28 Java-тестов проходят с отдельной тестовой PostgreSQL. Сборка `docker build -t e-game-stage6-app .` и образ ML с новыми зависимостями собраны; восемь ML-тестов проходят. Для локального Maven требуется Java 25; установленная на машине Java 17 уже не подходит.
2. На **нетронутой копии** базы эксперимента с Hibernate `ddl-auto=validate` новое приложение запустилось без изменения схемы. На другой копии проверены вход администратора, страницы `/admin/bot-experiments/20`, JSON-статус сохранённой серии, логин после перезапуска с JDBC-сессией и пилотная игра на 30 дней (2 бота, 60 строк статистики и продаж, 21 учебный эпизод).
3. Контрольный запрос последней рекламы на копии (~9 тыс. строк) до индекса: `Seq Scan`, 85 buffer hits и 1,003 мс исполнения одного запроса; после индекса: `Index Only Scan`, 4 hits и 0,129 мс. Это **один EXPLAIN на одной копии**, не обещание такого же ускорения полного игрового прогона.
4. Сопоставимые прогоны по трём играм, 10 ботов × 45 дней, `parallel=3`, одинаковый seed и список политик: старая Java 17/Spring Boot 2.5.6 без новых индексов и Java 25/Spring Boot 4.1.1 с индексами и виртуальными потоками дали одинаковые `seed`, статус `COMPLETED`, циклы, лучший результат и пропуски по каждой игре. Сравнение **всех 1350 ежедневных записей статистики** после дополнительного кэширования конкурентов: 0 расхождений. На копии старого контура накопилось 14 820 последовательных сканирований рекламы против 7 на новой копии (у новой дополнительно были две малые пробные игры); старые и новые счётчики не нормированы по одинаковой истории использования.
5. Наблюдение по приблизительному времени трёх игр: ~22 с на старой версии и ~11–16 с на новой при разных моментах опроса БД и прогреве. **Не считать это точным двухкратным ускорением**, или преимуществом именно виртуальных потоков: одновременно поменялись индексы, алгоритмы чтения, Java и Spring Boot. Для процентной оценки нужна повторная нагрузочная серия с записью времени старта/финиша каждого дня и раздельным A/B включения потоков.

## Эксплуатация и оставшиеся ограничения

- После успешной проверки оба рабочих контура обновлены через `docker compose up --build -d` с сохранением существующих томов; созданы индексы в обеих БД. Обычная игра (`:8080`) и эксперимент (`:8081`) отвечают на `/sign-in`; экспериментальный CatBoost после обновления сохранил `ready=true` и прежнюю версию. Серия № 20 после обновления **по-прежнему `PAUSED`**, 191 `COMPLETED`, 67 `INCOMPLETE`, 3 `QUEUED`, 0 `ERROR`; продолжать её можно штатной кнопкой. Хостовый `./mvnw` теперь требует установленную JDK 25, либо можно собирать контейнером.
- В `application.properties` пока сохраняется `spring.jpa.hibernate.ddl-auto=update` для первичного развёртывания; на двух **действующих** контурах через Compose установлен `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`, чтобы новый Hibernate не менял старые таблицы при запуске. При первом обновлении обычного контура до добавления этого параметра Hibernate успел расширить precision денежных `numeric(19,2)` до `numeric(38,2)` в маленькой базе (масштаб 2 не изменился); затем оба контура перезапущены в режиме `validate`. Переход к управляемым миграциям всей схемы и отказ от `update` по умолчанию остаются отдельной задачей.
- Старые JDBC-сессии Spring Security 5 **несовместимы** с Spring Security 7 (`SecurityContextImpl` имеет иной serialVersionUID) и при использовании прежней cookie вызывают HTTP 500. На копии проверено, что удаление именно старой сессии из `spring_session` (с каскадом атрибутов) возвращает штатный редирект на вход. В действующей экспериментальной БД удалена **одна** старая сессия, созданная до запуска новой версии; в обычной БД старых сессий не было. Администратору понадобится войти заново; новые JDBC-сессии сохраняются при перезапуске.
- Не реализованы групповые расчёты всех платежей и массовое обновление износа: они могут изменить финансовые/торговые правила и требуют отдельных эквивалентных тестов. По-прежнему нужен длительный профиль SQL и многократный A/B на одинаковых данных для оценки общего выигрыша и оптимального параллелизма. Доля `INCOMPLETE` меняется только новыми версионированными стратегиями/сериями, а не SQL-индексами.
