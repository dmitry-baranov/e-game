# Восьмой этап: модель данных эксперимента и правила ботов

> **Статус: проект итерации.** Продолжает [седьмой этап](STRATEGY_AGENTS_STAGE7_TASK.md). В этой итерации допускается пересоздать **экспериментальную** БД с нуля; существующие данные не являются требованием совместимости. Это разрешение на проектирование, а не команда удалять рабочую БД или перезапускать `:8081` сейчас. Обычный контур `:8080` и его БД в область сброса не входят.

## 1. Цель и исходные проблемы

Сохранить смысл игры (покупатель, деньги, кредиты, налоги, торговые дни), полноту учебного цикла, детерминированность seed и парность `EVALUATE`. Упростить схему и чтение результатов, уменьшить количество запросов **на день игры**, а не только ускорить отчёт, и дать каждой политике бота собственное понятное правило.

- `BotAnalyticsController.run()` повторяет 5–7 коррелированных подзапросов к `statistics_info` для каждого `production_parameters`, а `ExperimentReports.report()` пересчитывает наблюдаемые дни всех эпизодов. `ml/learning.py` повторно соединяет эпизоды, производителей, игры, серии и дневные продажи. В больших сериях стоимость этих расчётов растёт с размером истории.
- `StrategySnapshotService.snapshot()` читает последние параметры, рекламу, 7 продаж и платежи **для каждого бота**; `visibleCompetitors()` дополнительно читает производство и рекламу каждого соперника. `BotDecisions.observedCycles()` снова соединяет производства с дневной статистикой на каждом решении. Это кандидат на пакетное чтение одного игрового дня; индекс сам по себе не устраняет повторные обращения.
- `ExperimentEngine.reconcileWaitingPairs()` и `ExperimentManager.recover()` загружают все попытки серии и обходят их в Java. `BotAnalyticsController` держит SQL и сборку HTML-модели рядом с проверкой HTTP-параметров. `BotPolicies.expanded()` содержит большой `switch` на 32 политики и общую нормализацию результата; короткие `switch` навигации и операций серии в паттернах не нуждаются.
- Схему игровых и экспериментальных таблиц сейчас во многом создаёт Hibernate (`spring.jpa.hibernate.ddl-auto=update`); `schema.sql` содержит только таблицы сессий, а `performance_indexes.sql` запускается вручную. Для воспроизводимого пересоздания нужна одна версионированная схема.

## 2. Целевая модель данных

Не переносить расчёты торговли в отдельную «упрощённую» игру: обычные игровые сервисы остаются источником фактических продаж, платежей и результата. Переиспользуемые бот-аккаунты не должны смешиваться с состоянием конкретной игры.

| Сущность | Назначение и ограничения |
| --- | --- |
| `experiment_series` | Режим, статус, `config_json`, версии генератора/политик/модели, цель и следующий номер. `config_json` хранит исходную конфигурацию, а часто фильтруемые `target`, `mode`, `status` — отдельные столбцы. |
| `experiment_pair` | Только для `EVALUATE`: `series_id`, `pair_number`, `seed`, `market`, статус пригодности пары; `UNIQUE(series_id, pair_number)`. Это явная связь двух попыток вместо поиска по чётности `number`. |
| `experiment_run` | Попытка, `series_id`, необязательный `pair_id`, `game_id`, номер, статус, прогресс и агрегатные счётчики. `UNIQUE(series_id, number)`, уникальный `game_id` при наличии; CHECK на допустимые статусы, FK на серию/пару/игру. Статус пары вычислять по обеим половинам в транзакции, не считать половину отдельной успешной игрой. |
| `game`, `manufacturer`, `account` | Существующие игровые сущности; один `manufacturer` на `(game_id, account_id)`. Аккаунт бота — идентичность, `manufacturer` — баланс, склад и политика **в данной игре**. На новой пустой БД завести явный признак служебного аккаунта вместо распознавания его по email; скрывать его в форме обычной игры по этому признаку. |
| `production_parameters` / `production_cycle` | Один реальный принятый производственный цикл. Если игровую таблицу нельзя безопасно переименовать, оставить её как источник истины и добавить в ней явные `decision_log_id` (nullable для людей) и конец цикла. Не дублировать один и тот же план в двух пишущихся таблицах. |
| `statistics_info` | Факт `(manufacturer_id, trade_date)` с `UNIQUE` и FK; одна запись на бота и игровой день. Проверить, что механика игры действительно гарантирует эту кардинальность; иначе сначала определить способ учёта нескольких событий дня и агрегировать их в дневной факт. Отсутствующий день не равен нулевым продажам. |
| `bot_decision_log` | Решение по `(manufacturer_id, decision_day)` с outcome, policy, source/model/fallback, исходными snapshot/action/candidates и nullable FK к принятому циклу. Уникальность применять только если в игре не разрешены несколько попыток в один день; отклонённый план не создаёт цикл. |
| `strategy_training_episode` | Эпизод с `manufacturer_id`, `run_id` (nullable для обычной игры), `cycle_id` (nullable до принятия), днём решения, длительностью, snapshot/action. Только согласованные пары «снимок до решения → факт завершённого цикла» пригодны для обучения. |
| `cycle_observation` | **Одна** производная запись на принятый цикл: `cycle_id` unique, `observed_days`, `sold`, `produced`, `revenue`, платежи, `ending_stock`, `balance_change`, `complete`. Она создаётся/обновляется при коммите игрового дня; `complete` истинно только если наблюдаемы все требуемые дни без дублей. При повторе транзакции нельзя удвоить суммы. Источником для сверки остаётся `statistics_info`. |

Не добавлять отдельную таблицу для каждого из 38 правил: параметры правил и их имена — код/конфигурация версии политики, а не транзакционные данные. JSON оставить для воспроизводимых снимков и настроек, числовые поля, по которым фильтруют/соединяют, держать в типизированных столбцах. `training_run_report` создаётся и используется также Python-сервисом; его DDL и запросы `ml/learning.py` обновлять одновременно с Java, включая оба режима обучения (экспериментальные и согласованные обычные игры).

## 3. Доступ к данным и производительность

1. Для игрового шага собрать `GameDayReadModel` **одним пакетным чтением** по `game_id`: производителей, последние производства/рекламу, последние 7 дневных продаж на производителя, будущие платежи и завершённые собственные циклы. Построить отдельные снимки всех ботов в памяти **до** применения первого решения. Не дать боту увидеть скрытые параметры рынка или текущие решения соперников. После пакетного чтения сравнить состав снимка с текущим `StrategySnapshotService` на фиксированных играх.
2. Вынести SQL из `BotAnalyticsController` в `ExperimentReadRepository`/`BotAnalyticsReadRepository`; контроллер только проверяет параметры и передаёт типизированные DTO в шаблон. Сводку циклов и отчёт покрытия читать из `cycle_observation`, тяжёлые общесерийные агрегаты запрашивать по требованию (либо обновлять после завершения игры). Детали дня, платежей и журнала читать по выбранному боту, не на каждом обновлении статуса серии.
3. Для планировщика заменить проходы всей серии на запросы по статусу: `UPDATE ... WHERE series_id=? AND status='RUNNING'` при восстановлении с сохранением семантики возобновления; парные статусы — SQL по `pair_id` с блокировкой нужной строки, а не обход всех `experiment_run`. `claim` оставлять атомарным под блокировкой серии. Убрать раздельные `countBySeriesIdAndStatus` на каждом слоте через компактную сводку/счётчики только после проверки реальных планов и конкуренции.
4. Первоначальные индексы под реальные пути: `experiment_run(series_id,status,number)`, `experiment_run(pair_id)`, `manufacturer(game_id,id)`, `statistics_info(manufacturer_id,trade_date)` unique, `production_parameters(manufacturer_id,start_date DESC,id DESC)`, `bot_decision_log(manufacturer_id,decision_day)`, `strategy_training_episode(manufacturer_id,decision_day)`, платежи по ключу владельца и `next_date`. Проверить индексы FK и порядок сортировки. Не создавать все мыслимые индексы: каждый увеличивает стоимость записи игрового дня.
5. Проверить `EXPLAIN (ANALYZE, BUFFERS)` на типовой серии (много игр, 30+ дней, несколько ботов): отчёт, страница игры, чтение снимков, извлечение данных ML. Зафиксировать p50/p95 времени игрового дня, число SQL-вызовов на день и время отчёта **до/после** на одинаковой синтетической выборке; у запроса на новой пустой БД хороший план ещё не доказывает ускорение на большой серии.

## 4. Упрощение ветвлений политик

- Ввести `BotPolicy` (`name()`, `decide(PolicyContext)`) и реестр имён с явной ошибкой для неизвестной политики. `PolicyContext` содержит только видимый `StrategySnapshot`, собственные завершённые `ObservedCycle`, индекс и детерминированный генератор; новые поля добавлять лишь по потребности. Каждое правило возвращает **предложенный** план; общий `PlanNormalizer` один раз ограничивает цену, партию, качество, ассортимент и рекламу. Приём/отказ по складу и кредиту остаётся у движка.
- Не создавать 38 Spring-сервисов ради 38 строк. Короткие варианты объединить в тематические классы (`PricePolicies`, `StockPolicies`, `QualityPolicies`, `AdvertisingPolicies`, `FinancePolicies`, `RivalPolicies`); более сложные (`CONSERVATIVE_CASH_SCORE`, `PRICE_REVENUE_WINDOW`, `MODEL`) вынести в отдельные реализации. Реестр связывает **одно** имя с **одним** обработчиком, сам проверяет отсутствие дублей и полноту списка для UI. Источник метаданных (имя, описание, обработчик) должен быть единым вместо массива `NAMES` + карты `DESCRIPTIONS` + `switch`.
- `RULES`/`EVAL_RULES`/`MODEL` оформить отдельным адаптером к `StrategyCoordinator`: сохранение fallback, версии модели, карточек и фактического `usedModel`. Для специальных кредитных ограничений выбрать одну явную `CreditGuard`-политику/таблицу правил по имени, вызываемую из `ExperimentEngine`, вместо второго разрозненного `switch`; общая верхняя граница кредита применяется первой. Не объединять проверку финансовой допустимости с генерацией плана.
- Короткий `switch` в `ExperimentManager.change()` (pause/resume/stop) и переключатели обратных URL в `BotAnalyticsController` оставить простыми; паттерн там добавит больше кода, чем уберёт.

## 5. Порядок реализации

1. **Контракт поведения и замеры.** Зафиксировать сценарии `COLLECT`/`EVALUATE`, паузу/повтор, полный и неполный цикл, одновременные серии, совпадение seed пары, результат после долгов. Сохранить контрольные снимки и решения на фиксированных seed, а также планы запросов/метрики на отдельной тестовой БД.
2. **Версионированный DDL.** Описать миграции (например, Flyway) для PostgreSQL и тестовой БД, заменить `ddl-auto=update` на `validate` для новой схемы, привести `schema.sql` и ручной `performance_indexes.sql` к единому порядку применения. Убедиться, что приложение и Python ML поднимаются из пустой БД. До любого сброса согласовать конкретную БД, контейнер и том, остановить запись в неё и отдельно проверить, нужны ли сохранённые модельные артефакты. Разработку делать на новой отдельной БД; удаление рабочей истории — отдельный шаг после проверки.
3. **Запись и чтение.** Ввести ключи/ограничения, `cycle_observation`, пакетное чтение снимков, репозитории DTO и прямые связи пар; затем обновить Java, SQL страниц и Python ML вместе. Ежедневные факты и наблюдения фиксировать атомарно; без асинхронной очереди, пока замеры её не обосновали.
4. **Политики.** Вынести обработчики по группам и общий нормализатор, затем адаптер модели и кредитный guard. Сравнить решения, seed, fallback, принятие/отклонение и результаты на фиксированных сценариях до смены версии политики.
5. **Приёмка.** Поднять схему с нуля, запустить полный набор тестов и нагрузочную серию на изолированной PostgreSQL, сверить сводки `cycle_observation` с суммами дневных фактов, проверку полноты/дублей, ML-выборку и отчёты; повторить замеры из шага 1. Только затем обсуждать пересоздание экспериментального рабочего контура.

## 6. Критерии готовности

- Пустая БД создаётся одним воспроизводимым набором миграций; веб-приложение, ML и оба режима обучения используют одну согласованную схему.
- В игре нет лишних запросов на каждого бота сверх согласованного пакетного чтения, а отчёты не сканируют все дни каждого цикла повторно; подтверждено количеством SQL-запросов, планами и p50/p95 на одинаковой нагрузке.
- Дневные факты, принятие решения, наблюдение цикла и счётчики не расходятся после отката, повтора дня или параллельной игры; нулевые продажи отличимы от отсутствующего дня.
- `EVALUATE` включает в эффект только две пригодные игры одного seed/рынка, модельный fallback не считается применением модели. Снимки ботов и финансовые результаты остаются сопоставимыми с контрольными сценариями; изменения поведения, если они желательны, оформляются отдельной версией политики/генератора.
