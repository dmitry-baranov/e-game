# Шестой этап: диагностика и ускорение симуляции экономической игры

> **Статус: анализ и задание, не внедрённая оптимизация.** Продолжает [пятый этап](STRATEGY_AGENTS_STAGE5_TASK.md). Цель — увеличить число **полных, пригодных для обучения игр в час** при тех же правилах, исходных данных и составе ботов. Отдельно оценить виртуальные потоки, базу данных и накладные расходы каждого торгового дня. Рабочую серию № 20 не изменять задним числом.

## 1. Что установлено на действующей среде

Снимок во время работы серии № 20 (09.10.2026): `RUNNING`, 245 начатых игр, 181 `COMPLETED`, 61 `INCOMPLETE`, 0 `ERROR`, 3 активных; база эксперимента — около 276 MB. Числа меняются во времени. Серия настроена на 10–20 ботов и три параллельные игры; один рабочий поток обрабатывает игру по дням, каждый день — отдельная транзакция (`ExperimentManager.execute`, `ExperimentEngine.advance`). Неполные игры не входят в целевые 1000 завершённых и создают заметную дополнительную работу: на этом снимке 61 из 242 уже закончившихся попыток (~25%). Причина `INCOMPLETE` — недостаточно полных производственных циклов хотя бы у одного бота, а не обязательно ошибка/замедление сервера.

Накопительная статистика **всей экспериментальной БД, а не только серии № 20** (`pg_stat_user_tables`, счётчики с момента их последнего сброса):

| Таблица | Примерное число живых строк | `seq_scan` | Индекс по характерному запросу |
| --- | ---: | ---: | --- |
| `advertisement` | 9 тыс. | 4,93 млн | только PK `id` |
| `business_credit_payment` | 16 тыс. | 1,09 млн | нет пользовательских индексов |
| `investment_credit_payment` | 18 тыс. | 766 тыс. | нет пользовательских индексов |
| `trading_session_results` | 421 тыс. | 306 тыс. | только PK `id` |
| `production_parameters` | 52 тыс. | 246 тыс. | есть `(manufacturer_id, start_date)` |

Контрольный `EXPLAIN (ANALYZE, BUFFERS)` на **одном** чтении `advertisement WHERE manufacturer_id = …`: `Seq Scan`, ~9158 отброшенных строк, 83 прочитанных из общего буфера страниц, ~0,60 мс исполнения. Это доказательство конкретного плана, **не** среднее время всех запросов и не оценка будущего ускорения. Миллионы `seq_scan` — накопленная активность, а не доказательство, что каждый такой запрос одинаково дорог. `pg_stat_statements` сейчас не подключён (`shared_preload_libraries` пуст, расширение отсутствует), поэтому точное распределение времени между SQL и Java ещё не измерено.

Предыдущая проверка ресурсов показывала высокий CPU PostgreSQL (~243%) и приложения (~107%) при небольшом использовании памяти; это совместимо с затратами на повторные запросы и обработку, но не доказывает долю каждого компонента. Не увеличивать параллелизм исходя только из процента CPU. Дополнительная сложность нагрузки: при 10–20 ботах каждый торговый день создаёт записи продаж/статистики на каждого бота и выполняет для них подготовку, расчёты и платежи.

## 2. Конкретные причины и гипотезы по исходникам

1. **Сканирование таблиц и многократная загрузка истории (высокий приоритет).** `ManufacturerServiceImpl.getLastAdvertisement` и `getLastProductionParameters` загружают всю историю производителя и ищут максимум в Java; `getCompetitorsData` вызывает загрузку последнего производства и рекламы для каждого соперника. `StrategySnapshotService.snapshot` снова читает всю историю производства/рекламы, продажи перед `.limit(7)`, историю кредитов и список конкурентов. `ExperimentEngine.advance` создаёт снимок отдельно для каждого бота, а значит один и тот же набор конкурентов собирается многократно в один день. `TradingSessionService.calculateValue` дополнительно ищет рекламу каждого производителя при сортировке. Проверить SQL-count на бот/день, а не утверждать без замера точный N+1 множитель.
2. **Запросы, растущие с историей игры.** `BuyerService.updateWornOutFlag` получает все неистёртые покупки игры, обновляет истёкшие по одной записи через `save`; `getUnwornProductsCountByGameId` агрегирует остаток. `TradingSessionService.getPurchaseCountsByManufacturerId` читает отдельные записи продаж за интервал, хотя для привычки нужны суммы. `PaymentService.makeBusinessCreditPayments` и `ManufacturerServiceImpl.calculateManufacturerBusinessCreditDebt` каждый раз сначала читают все производственные циклы, затем ищут платежи по списку их ID. `ExperimentEngine.observedCycles` выполняет агрегирующий SQL на каждый выбранный цикл решения; проверить план и индекс `statistics_info(manufacturer_id, trade_date)` (он уже есть).
3. **Ненужная загрузка и запись внутри каждого дня.** `TradingSessionService` несколько раз запрашивает список производителей; `PaymentService` делает это отдельно для каждого вида платежа, даже в дни без ежемесячного налога. `BuyerService.makePurchases` создаёт строку `trading_session_results` даже при нулевых продажах — менять только после проверки, что аналитика, износ и контракт данных не зависят от такой строки. `StrategyTrainingCapture` и `ExperimentEngine.logDecision` сериализуют снимки/действия и вставляют эпизоды/журнал; эти данные нужны для обучения и диагностики, их нельзя просто отключить ради скорости.
4. **Накладные расходы планировщика.** Каждую секунду `ExperimentManager.dispatchSafe` перечисляет все серии; `ExperimentEngine.claim` под блокировкой серии считает завершённые/активные игры и загружает все игры серии ради поиска `QUEUED` (и для оценки пары). С ростом числа попыток это может стать заметно; проверить профилем, но не считать главной причиной без измерений. `workers` — пул из десяти платформенных потоков, а фактический максимум серии № 20 — три; изменение размера пула само по себе не увеличит параллельность.
5. **Доля неучебных попыток.** 61 `INCOMPLETE` на момент снимка расходуют полные игровые дни. Отдельно исследовать `STOCK_SKIP`/`CREDIT_SKIP`, размер партии, остаток и длину цикла: улучшение **новых**, версионированных политик/генератора может повысить полезную пропускную способность, но меняет данные и результаты эксперимента. Нельзя задним числом засчитать неполную игру полной или сокращать её горизонт только для ускорения.

## 3. Виртуальные потоки: решение для данного стека

**Сейчас напрямую применять нельзя:** `Dockerfile` запускает Java 17, `pom.xml` указывает Spring Boot 2.5.6, `java.version=11` и компиляцию `source/target=16`. Стабильные виртуальные потоки появились в Java 21 (JEP 444); переключателя `spring.threads.virtual.enabled=true` в используемой версии Boot нет. Целевой маршрут шестого этапа — переход на **Java 25** и актуальный стабильный Spring Boot с поддержкой Java 25, вместе с миграцией зависимостей и `javax.*` → `jakarta.*`, проверкой сборки, JDBC/транзакций и Spring Session. Это отдельная техническая миграция, не быстрая правка одного флага.

Даже после миграции виртуальные потоки обычно помогают **масштабировать ожидание I/O**, а не ускоряют один SQL-запрос или CPU-вычисление. Здесь игра последовательно обрабатывает дни; `TransactionTemplate` и Hibernate привязаны к контексту текущего потока, `StrategyTrainingCapture` использует `ThreadLocal`, а внешняя граница серии — три игры. Перенос обработки отдельных ботов одного дня на параллельные потоки без перепроектирования транзакции и механики «все снимки до решений» нарушит корректность. При неизменном лимите трёх игр ожидаемый выигрыш от замены трёх рабочих потоков виртуальными минимален; больше одновременно работающих игр может увеличить конкуренцию за соединения, блокировки и CPU PostgreSQL. Не задавать численный процент ускорения без A/B измерения. Перенос `ThreadLocal` между потоками и JPA-сессиями требует отдельной проверки; не передавать persistence context между потоками.

**Вывод:** сначала измерить и оптимизировать SQL и повторные чтения; виртуальные потоки рассматривать позднее как отдельный эксперимент после перехода на Java 25 при действительно большом числе ожидающих I/O игр, с ограниченным пулом соединений и управляемым параллелизмом. Отдельно сравнить платформенные и виртуальные потоки при **одинаковых** `parallel`, пуле БД и наборе seed; повышение `parallel` проверять отдельным тестом.

### 3.1. План обновления платформы и всех зависимостей

По [официальным требованиям Spring Boot](https://docs.spring.io/spring-boot/system-requirements.html) на дату подготовки документа актуальный стабильный ориентир — **Spring Boot 4.1.1**, совместимый с Java 25 (заявлена поддержка Java 17–26). При фактической миграции заново проверить официальный последний **stable**, а не автоматически брать preview/snapshot, и зафиксировать точные версии и дату выбора. Обновление платформы — требование этапа независимо от решения включать виртуальные потоки.

1. Снять список прямых и транзитивных зависимостей `pom.xml` и `ml/requirements.txt`, Maven-плагинов/обёртки и базовых образов `Dockerfile`, `ml/Dockerfile`, `compose*.yml`; отметить неиспользуемые библиотеки и несовместимые/неподдерживаемые артефакты. Выбрать совместимые актуальные **стабильные** версии, зафиксировать итоговый список «было → стало», источник версий, список замены удалённых библиотек. «Обновить всё» означает весь действительно используемый стек, а не механически проставить последний номер у каждой библиотеки.
2. Перевести компиляцию и запуск на Java 25: согласовать `java.version`, `maven-compiler-plugin` с `release=25`, Maven wrapper и плагины, локальную/CI JDK и build/runtime образы. Убрать противоречие между текущими `java.version=11`, `source/target=16` и Java 17 в Dockerfile; тестировать именно собранный Java 25 артефакт внутри контейнера.
3. Перейти на актуальный stable Spring Boot, пользуясь его BOM для управляемых версий; убрать старые ручные закрепления `postgresql 42.2.5`, Jackson 2.12.5, `validation-api 2.0.1.Final`, `hibernate-validator 6.2.0.Final` там, где зависимости управляются BOM. Для `jsonwebtoken 0.9.1`, `zip4j 2.7.0`, `commons-io 2.8.0`, `commons-fileupload 1.4` и Lombok выбрать поддерживаемые версии либо заменить API/зависимость при несовместимости. Проверить, не зависит ли код от Jackson 2 API при переходе на Boot 4 (версии/модули Jackson и сериализацию JSON закрепить явно после тестов).
4. Пройти совместимость **по основным версиям**: `javax.persistence`/`javax.servlet`/`javax.validation`/`javax.annotation` → Jakarta API, Spring Security и конфигурация логина/ролей, Spring Data JPA и Hibernate (SQL, таблицы/колонки, ленивые связи, генерация ID), Spring Session JDBC и схема существующих сессий, FreeMarker, контроллеры/валидация, сериализация DTO, `TransactionTemplate` и журнал обучения. Старое `spring.jpa.hibernate.ddl-auto=update` не считать механизмом безопасной миграции рабочих данных: изменения схемы проверять на копии БД, оформлять воспроизводимыми миграциями и планом отката.
5. Обновить также Python-зависимости ML-сервиса (`flask`, `gunicorn`, `psycopg2-binary`, `numpy`, `scikit-learn`, `catboost`, `lightgbm`, `joblib`) до взаимно совместимых стабильных версий, Python-образ и PostgreSQL JDBC/клиент, с проверкой установки на используемой архитектуре (в том числе arm64), загрузки сохранённых моделей и воспроизводимости инференса/обучения. Формат ранее сохранённых моделей может требовать пересборки: сверять на отдельной копии артефактов, не перезаписывать действующие.
6. Проверить `./mvnw test` и ML-тесты, сборку обоих контейнеров, запуск обычной и экспериментальной игры на **отдельных копиях данных**, аутентификацию, создание/пауза/возобновление игр, сохранённые серии, учебные эпизоды, HTTP-страницы, отчёты и независимую оценку ML. Сравнить метрики из раздела 4 **до/после миграции** при одинаковых seed/нагрузке; если меняются правила игры или результаты, выяснить причину до замены рабочего контура. Обновлять рабочий эксперимент только после завершения/штатной паузы серии и проверки сохранности данных; тома БД не удалять.

Обновление Java и Spring Boot само по себе не гарантирует ускорения. После миграции виртуальные потоки включать и оценивать отдельно: это позволит различить эффект версии JVM/библиотек и эффект модели исполнения.

## 4. Порядок оптимизации и способы доказать выигрыш

| Приоритет | Работа | Проверка результата и корректности |
| --- | --- | --- |
| P0 | Снять baseline: игры/час (`COMPLETED` отдельно от попыток), дни/с, p50/p95 времени дня и полного прогона, число SQL/день и бот/день, CPU/IO/ожидания БД, размер таблиц, долю `INCOMPLETE`; фиксировать ботов, горизонт, рынок, seed и число параллельных игр. Для SQL — Hibernate statistics/DataSource instrumentation на тестовой среде, выборочные `EXPLAIN (ANALYZE, BUFFERS)` и при необходимости `pg_stat_statements` на **отдельном** контуре (для него нужен рестарт PostgreSQL). | Профиль идентифицирует самые дорогие операции по **суммарному времени**, не только по числу запросов; сбор метрик не портит текущие данные. |
| P1 | Проверить планы и добавить недостающие индексы по реальным предикатам: `advertisement(manufacturer_id, start_date DESC, id DESC)`, `trading_session_results(manufacturer_id, trade_date)`; для износа/неизношенных строк оценить частичный индекс по `is_worn_out=false` с учётом JOIN по игре; для кредитов — `investment_credit_payment(manufacturer_id, next_date)`, `business_credit_payment(production_parameters_id, next_date)`; индекс производителя по `game_id` проверить прежде чем добавлять. | `EXPLAIN` до/после, размер индексов и стоимость вставок; не создавать дубликаты уже имеющихся индексов. Деплой индексных изменений оформить воспроизводимой миграцией для обоих контуров; на загруженной БД учесть безопасный способ создания (`CONCURRENTLY` вне транзакции). |
| P1 | Заменить загрузку всей истории ради последней записи на ограниченный `ORDER BY start_date DESC, id DESC LIMIT 1`; продажи снимка ограничивать **SQL `LIMIT 7`**; суммы привычки/неизношенных покупок/задолженности агрегировать в БД вместо материализации всех строк. | Совпадение значений на реальных сохранённых играх, в том числе при одинаковых датах, нулевых продажах, частичных оплатах и пропущенной рекламе; число считанных строк и SQL/день снижается. |
| P2 | Собирать неизменяемый снимок общего состояния конкурентов и нужные данные по всем производителям раз в день, а не за каждого бота; передавать уже загруженный список производителей в стадии торговли/платежей; группировать поиск активных платежей и обновление истёртых покупок. | Все боты по-прежнему видят только разрешённые данные **до** применения решений этого дня; налог, баланс, износ, продажи и время завершения циклов совпадают с baseline. Для `BuyerService.updateWornOutFlag` изменение на bulk UPDATE требует аккуратного сброса/синхронизации persistence context. |
| P2 | Уменьшить накладные расходы диспетчера: выбор активных серий и первого `QUEUED` через ограниченные запросы/индексы; считать статусы агрегатом вместо загрузки всех игр, не нарушая блокировки `claim` и парность `EVALUATE`. Рассмотреть JDBC batch insert/update для ежедневных записей после замера; Hibernate `IDENTITY`-генерация может ограничить batching. | Нет двух claim одной игры, нет дублей дней после restart/pause, серия завершается по прежним правилам. |
| P3 | Плановая миграция на Java 25, актуальный stable Spring Boot и все совместимые зависимости по § 3.1; отдельно изолированный эксперимент с `parallel=1/2/3/4/6` и, после миграции, с виртуальными потоками **на копии среды**. | Построить кривую `COMPLETED`/час и p95 дня, CPU/ожидания/соединения; оставлять новый режим только при доказанном улучшении без сбоев/изменения детерминированных результатов. |

Разделить два эффекта: **ускорение вычисления одной и той же игры** и **повышение процента полных игр изменением политики**. Для первого нужны одинаковые seed, конфигурация и версии генератора/политик; проверять результаты (продажи, balances, долги, `BotDecisionLog`, учебные эпизоды, статус каждого дня) и возможность продолжить после паузы/рестарта. Для второго проводить отдельные пилоты новых серий с версией правил и отчётом о смещении состава выборки. Оптимизации запросов и индексов вначале отработать на копии экспериментального контура; обычная игра использует те же сервисы, поэтому проверить её регрессионными сценариями.

## 5. Итоговое решение

Наиболее обоснованная первая точка приложения усилий — **запросы рекламы, платежей, продаж и повторное построение снимков**: по ним есть и указания в коде, и накопленные сканирования таблиц, и подтверждённый последовательный план чтения рекламы. Точный выигрыш не измерен. Наращивание потоков до исправления этого слоя может лишь нагрузить PostgreSQL сильнее. Критерий готовности шестого этапа — воспроизводимый baseline, профиль SQL, серия небольших изменений с измерением `COMPLETED`/час и неизменностью правил игры; решение о виртуальных потоках принимать по результату отдельного измеренного прототипа после обновления стека.
